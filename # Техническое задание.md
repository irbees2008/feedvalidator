# Техническое задание
# NGCMS Lab — развитие существующего проекта

**Версия документа:** 2.1  
**Основа проекта:** Python Feed Validator  
**Текущая среда разработки:** Windows + OSPanel  
**Текущий способ запуска:** Apache CGI  
**Основной язык серверной части:** Python 3.12  
**Языки интерфейса:** HTML, CSS, JavaScript  
**Система контроля версий:** Git (локальный репозиторий)

---

## 1. Общая концепция проекта

NGCMS Lab — набор бесплатных онлайн-инструментов для веб-мастеров, SEO-специалистов, разработчиков и администраторов сайтов.

Проект уже существует и построен на базе открытого исходного кода Feed Validator, первоначально разработанного Сэмом Руби и Марком Пилгримом.

В процессе развития к исходному валидатору были добавлены собственные инструменты, страницы, интерфейс и дополнительные функции.

**Основная задача — не создавать новый проект с нуля, а последовательно развивать существующий NGCMS Lab.**

Необходимо сохранить:
- исходную функциональность Feed Validator;
- существующую структуру проекта там, где она не мешает развитию;
- работающие инструменты;
- текущий дизайн и оформление сайта;
- совместимость с локальной средой OSPanel;
- возможность дальнейшего размещения на Apache-хостинге.

### Главный принцип разработки

Не переписывать работающий код без технической необходимости.

Новые инструменты добавлять отдельными модулями. Существующие компоненты изменять только после анализа зависимостей и проверки совместимости.

## 2. Текущая структура и технологии

### 2.1. Серверная часть

Основой является Python Feed Validator.

Сейчас используются:
- Python 3.12;
- Apache CGI;
- собственные CGI-обработчики;
- библиотека Feed Validator;
- feedparser;
- lxml;
- certifi.

Зависимости проекта определяются через `requirements.txt`.

Текущая архитектура не основана на Flask, Django или FastAPI. Внедрять подобный фреймворк только ради модернизации не требуется.

### 2.2. Клиентская часть

Используются:
- HTML;
- CSS;
- JavaScript;
- существующие стили и шаблоны;
- локальные библиотеки и ресурсы проекта.

Часть инструментов полностью выполняется в браузере, без обращения к серверу.

### 2.3. Текущие компоненты

В проекте уже присутствуют:

| Инструмент | Текущее назначение |
|---|---|
| Feed Validator | Проверка RSS и Atom |
| KML/XML | Проверка поддерживаемых XML-форматов |
| Open Graph Checker | Анализ Open Graph и Twitter Card |
| Base64 | Кодирование и декодирование Base64 |
| URL Encoder | Кодирование и декодирование URL |
| Favicon Generator | Создание favicon, PNG, ICO и manifest |
| Markdown Editor | Редактор Markdown с предпросмотром |
| Fancy Text | Генератор декоративного Unicode-текста |

Дополнительно присутствуют:
- предпросмотр RSS/Atom;
- диагностическая информация об HTTP-ответе;
- отображение первых записей ленты;
- генерация Open Graph-разметки;
- предпросмотр социальных карточек;
- экспорт результатов отдельных инструментов.

Перед изменением любого из этих компонентов необходимо проверить его фактическую реализацию и сохранить существующее поведение.

## 3. Архитектура дальнейшего развития

### 3.1. Общий подход

Сохранить Python в качестве основного серверного языка.

PHP не использовать для переписывания существующих компонентов.

NGCMS Lab должен развиваться как самостоятельный проект, не требующий установки NGCMS.

### 3.2. Принцип модульности

Каждый новый серверный инструмент должен иметь отдельную реализацию.

Предполагаемое логическое разделение:

- Feed Tools — RSS, Atom, XML, KML;
- SEO Tools — Open Graph, Meta, Schema.org;
- HTTP Tools — HTTP-запросы, заголовки, перенаправления;
- DNS Tools — DNS и сетевые проверки;
- Developer Tools — JSON, JWT, Regex и другие инструменты;
- Security Tools — проверка HTTP-заголовков и базовых параметров безопасности;
- NGCMS Tools — инструменты для разработки и обслуживания NGCMS.

Это логическое разделение. Оно не требует немедленного переноса всех существующих файлов в новые каталоги.

### 3.3. Подключение новых инструментов

Для каждого инструмента необходимо предусмотреть:

1. Отдельную страницу или интерфейсный блок.
2. Собственный JavaScript при необходимости.
3. Отдельный Python-модуль, если требуется серверная обработка.
4. Проверку входных данных.
5. Обработку ошибок.
6. Понятный результат для пользователя.
7. Возможность независимого тестирования.

Если существующий CGI-подход подходит для реализации нового инструмента, его можно использовать.

При появлении достаточного количества новых серверных инструментов допускается разработка общего JSON API и единого механизма маршрутизации.

**Переход на API не должен быть обязательным условием добавления каждого нового инструмента.**

### 3.4. База данных

На первом этапе база данных не требуется.

Результаты проверок должны формироваться непосредственно во время выполнения запроса.

Базу данных можно добавить позднее, если появится необходимость в:
- личных кабинетах;
- истории проверок;
- сохранении результатов;
- пользовательских настройках;
- статистике использования;
- управлении инструментами через административную панель.

## 4. Планируемые инструменты

Новые функции разделяются по назначению и приоритету.

#### 4.1.1. HTTP Status Checker

Проверка доступности сайта или отдельной страницы.

Функции:
- HTTP-статус;
- время ответа;
- конечный URL после перенаправлений;
- количество перенаправлений;
- HTTP-заголовки;
- тип содержимого;
- размер ответа;
- информация об ошибках соединения.

Дополнительно:
- проверка HTTPS;
- отображение цепочки перенаправлений;
- возможность копирования результатов.

#### 4.1.2. Robots.txt Validator

Проверка файла robots.txt.

Функции:
- загрузка по URL;
- вставка содержимого вручную;
- проверка синтаксиса;
- поиск ошибок и подозрительных директив;
- отображение Sitemap;
- анализ User-agent;
- проверка Allow и Disallow.

Результат должен содержать объяснение обнаруженных проблем.

#### 4.1.3. Sitemap Validator

Проверка XML Sitemap.

Функции:
- загрузка Sitemap по URL;
- загрузка XML-файла;
- вставка XML вручную;
- проверка XML-структуры;
- проверка обязательных элементов;
- анализ URL;
- поиск дублирующихся записей;
- проверка дат lastmod;
- поддержка Sitemap Index;
- проверка ссылок на вложенные Sitemap.

При необходимости предусмотреть ограничение количества проверяемых URL.

## 7. Общие требования безопасности

Безопасность является обязательной частью разработки.

### 7.1. Защита от SSRF

Все инструменты, которые загружают данные по пользовательскому URL, должны использовать единый безопасный механизм сетевого доступа.

Требования:
- разрешать только HTTP и HTTPS;
- запрещать обращения к loopback;
- запрещать private и link-local IP;
- блокировать служебные и зарезервированные диапазоны;
- проверять DNS-ответы;
- проверять IP после каждого перенаправления;
- ограничивать количество перенаправлений;
- ограничивать время соединения;
- ограничивать размер ответа;
- проверять тип содержимого;
- запрещать нестандартные порты, если они не нужны инструменту.

Особое внимание уделить существующему Feed Validator и его загрузчику URL.

За основу можно использовать уже реализованные защитные механизмы Open Graph Checker, предварительно проверив их полноту.

### 7.2. Защита файлов

- ограничивать размер загружаемых файлов;
- проверять расширение и фактический формат;
- не исполнять загруженные файлы;
- использовать временные файлы с безопасными именами;
- удалять временные файлы после обработки;
- ограничивать количество файлов за один запрос.

### 7.3. Защита от XSS

- экранировать пользовательские данные;
- безопасно выводить HTML;
- проверять ссылки;
- не вставлять пользовательский HTML без обработки;
- разделять исходные данные и готовую разметку.

### 7.4. Ограничения запросов

Предусмотреть:
- тайм-ауты;
- ограничения размера;
- ограничения количества запросов;
- защиту от чрезмерно долгой обработки;

NGCMS Lab должен быстро загружаться и не создавать лишнюю нагрузку.

- не выполнять повторные запросы без необходимости;

- оптимизировать изображения и статические ресурсы.

## 13. Правила работы над проектом

Все изменения должны выполняться с учётом следующих правил:

1. Перед изменением файла сначала изучить его содержимое.
2. Проверить, какие компоненты используют изменяемый код.
3. Не переписывать рабочие функции без необходимости.
4. Не заменять существующие библиотеки только ради обновления архитектуры.
5. Не удалять файлы, пока не подтверждено, что они не используются.
6. Не переносить файлы в новые каталоги без необходимости.
7. Не менять дизайн всего сайта при добавлении одного инструмента.
8. Не добавлять базу данных без конкретной потребности.
9. Не внедрять PHP вместо Python.
10. После каждого изменения проверять работоспособность затронутых компонентов.
11. При обнаружении ошибки сначала определить причину, а не маскировать её дополнительным кодом.
12. Все изменения должны быть совместимы с текущим способом локального запуска.

Для каждого этапа разработки необходимо предоставлять:

- список изменяемых файлов;
